## 2. 背景と目的

ウェアラブル端末等から得られる歩数、心拍、睡眠データだけでは、値が変化した理由や、その時の本人の感情を判断できない。本システムは、健康データから通常と異なる、または研究上確認対象となる状態を検出し、時間を空けずに参加者へ質問することで、センサーデータと主観回答を対応付けて研究用データとして蓄積する。

目的は次のとおりとする。

- Fitbit、Google HealthまたはCSVから参加者の健康データを継続取得する。
- 歩数、心拍、睡眠時間の変化をルールベースで検出する。
- 検出した時刻・区間について、SlackまたはKebbiを通じて行動と感情を質問する。
- センサーデータ、検出結果、質問、回答を一貫した参加者IDとイベントIDで保存する。
- 研究者が分析可能なCSV形式でデータを取り出せるようにする。

本システムの検出結果は医学的診断、疾病予測、緊急通報を目的としない。

## 3. ステークホルダー

| 区分 | 役割・関心 |
|---|---|
| 研究責任者 | 研究目的、検出基準、質問内容、データ利用方針を決定する |
| システム運用者 | 参加者、認証情報、基準値、Slack連携、定期処理を設定・監視する |
| 研究参加者 | ウェアラブル端末を装着し、SlackまたはKebbiからの質問に回答する |
| データ分析者 | CSVを取得し、センサーデータと主観回答を分析する |
| 開発・保守担当者 | API、収集処理、検出処理、通知チャネルを保守する |

## 4. 対象範囲

### 4.1 対象

- 複数参加者の属性情報管理
- Fitbit、Google Health、CSVからのデータ取得
- 集計済みおよび未加工のセンサー・睡眠データ保存
- 歩数、心拍、睡眠時間に基づくイベント検出
- イベントの重複抑止、期限、通知対象選定
- Slack DMによる二段階の自由記述質問
- Kebbiによる質問・回答の手動実験フロー
- 質問時刻、回答時刻、回答遅延の保存
- 研究分析用CSV出力
- Kebbi端末を外部から操作するAndroidソケットサーバー

### 4.2 対象外

- 医療診断、治療方針の提示、救急機関への自動連絡
- Fitbit/Google/Slackアカウントの新規発行
- 研究参加同意の取得・管理
- 大規模商用運用向けの高可用性構成
- ブラウザ用の管理画面・参加者画面
- 統計モデルや機械学習による異常検知
- SQLite以外の研究データストアへの同期

## 5. 前提条件・制約

- 日時の判定と表示は原則として日本標準時（JST、UTC+09:00）を用いる。
- バックエンドはPython/FastAPI、保存先はローカルSQLiteとする。
- 定期収集間隔は15分固定、センサーデータの主要集計単位は30分とする。
- 外部APIの利用には、参加者ごとのOAuth認証情報が必要である。
- SlackはSocket Modeを利用し、公開HTTPSエンドポイントを必須としない。
- Slack Botと定期収集処理は、同一SQLite DBへ直接アクセスできる環境で稼働する。
- Kebbiは同一ネットワーク上のPCからTCP接続できることを前提とする。
- 公開統計基準値は研究責任者が妥当性を確認したCSVを投入する。
- 実DB、OAuthトークン、Slackトークン、参加者とSlackの対応表をソース管理へ登録してはならない。

## 6. 業務フロー

1. 運用者が参加者ID、性別、年齢、取得元、認証情報を設定する。
2. システムが15分ごとに健康データを取得し、参加者IDと時刻を付けて保存する。
3. システムが保存済みデータを検査し、確認対象イベントを登録する。
4. システムが期限、睡眠中、静穏時間、質問間隔、イベント連続性を評価して通知可否を決める。
5. SlackまたはKebbiが対象参加者へ「何をしていたか」を質問する。
6. 参加者の一つ目の回答後、「どんな気持ちだったか」を質問する。
7. システムが二つの回答、質問時刻、回答時刻、回答遅延をイベントへ紐付けて保存する。
8. データ分析者が研究分析用CSVを取得する。

## 8. 非機能要件

### 8.1 性能・容量

| ID | 要件 |
|---|---|
| NFR-001 | 通常の定期処理は、次回15分周期までに完了すること |
| NFR-002 | APIのローカルDB操作は、通常データ量において原則3秒以内に応答すること |
| NFR-003 | MVPの想定規模は少人数の研究参加者とし、単一SQLite DBで運用可能な範囲とすること |

### 8.2 可用性・障害対応

| ID | 要件 |
|---|---|
| NFR-101 | 参加者1名または外部サービス1種の取得失敗が、他参加者の処理を妨げないこと |
| NFR-102 | Slack送信失敗時はイベントを未送信のまま保持し、次回以降に再試行可能なこと |
| NFR-103 | 同一データの再投入で不整合や重複を生じないこと |
| NFR-104 | SQLite DBを定期的にバックアップできる運用手順を設けること |

### 8.3 セキュリティ・プライバシー

| ID | 要件 |
|---|---|
| NFR-201 | OAuthおよびSlackトークンは`.env`等の非公開領域に保存すること |
| NFR-202 | ログへトークン、回答本文、不要な個人情報を出力しないこと |
| NFR-203 | 参加者とSlack IDの対応表をアクセス制限された設定ファイルで管理すること |
| NFR-204 | APIを外部公開する場合は、認証、TLS、アクセス元制限を追加すること |
| NFR-205 | 研究終了時の保存期間、匿名化、削除方法を研究計画に従って定めること |

### 8.4 保守性・運用性

| ID | 要件 |
|---|---|
| NFR-301 | 外部API認証情報を参加者単位の環境変数接頭辞で分離できること |
| NFR-302 | 収集元、参加者、遡及日数をJSON設定で変更できること |
| NFR-303 | 取得件数、検出件数、通知結果、エラーを運用ログで確認できること |
| NFR-304 | 書込みを行わず取得内容を確認するdry-runを提供すること |
| NFR-305 | DBスキーマの変更は既存データを保持する移行方式で行うこと |

## 9. 受入条件

| ID | 受入条件 |
|---|---|
| AC-001 | 設定した参加者について、CSVまたは外部APIからセンサーデータがDBへ登録される |
| AC-002 | 同じデータを2回投入しても、対象テーブルの論理的な行数が増加しない |
| AC-003 | 30分歩数2,000歩以上の増加、30分200歩未満の条件から想定イベントが作成される |
| AC-004 | 年齢と睡眠時心拍が存在する場合、心拍予備能基準を超えた覚醒中最大心拍からイベントが作成される |
| AC-005 | 性別・年齢・基準値が存在する場合、1日歩数と睡眠時間の比較イベントが作成される |
| AC-006 | Slack送信成功後にイベントが`asked`となり、送信失敗時は`pending`に残る |
| AC-007 | Slackで2回回答すると、行動・感情・回答遅延が同一イベントに保存される |
| AC-008 | Bot再起動を挟んでも二つ目の回答を保存できる |
| AC-009 | 静穏時間、睡眠中、クールダウン中の通知が仕様どおり抑止される |
| AC-010 | 出力CSVをWindows版Excelで開き、日本語、行動回答、感情回答を確認できる |
| AC-011 | 外部APIまたはSlackが失敗しても、他参加者の収集・検出処理が継続する |
| AC-012 | 実トークンや実参加者マッピングがバージョン管理対象に含まれない |

## 10. 未確定事項・要決定事項

以下は現行実装だけでは業務要件として確定できないため、研究責任者・運用者の承認が必要である。

1. 正式なシステム名称と、Kebbi/Slackのどちらを標準質問チャネルとするか。
2. 参加者数、研究期間、1参加者あたりの想定データ量。
3. 検出閾値と質問文の研究上の妥当性、および変更承認手順。
4. 「通常イベント」も質問する研究設計の妥当性と、質問サンプリング頻度。
5. 回答期限、無回答時の再通知回数、参加者が回答を訂正する方法。
6. 個人情報・健康データの保存期間、匿名化方式、削除依頼への対応。
7. API認証、端末暗号化、DB暗号化、バックアップ保管先。
8. 障害監視、通知先、復旧目標時間、データ欠損時の扱い。
9. Google Health APIの正式なデータ型・提供条件と、本番利用時の継続性。
10. 現行コード中のイベント説明文に文字化けした箇所があり、正式文言の確認が必要。
